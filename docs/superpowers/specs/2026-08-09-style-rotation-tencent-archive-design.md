# Style Rotation Tencent Archive Design

## Goal

让市场估值邮件与红利观察邮件中的风格轮动区块，针对 `399376`（国证小盘成长）与 `399373`（国证大盘价值）两只特殊指数，改走腾讯源并具备本地归档兜底，避免运行时完全依赖临时实时抓取。

## Scope

本次只处理风格轮动使用的两个特殊指数：

- `399376`
- `399373`

不改动其它估值指数的现有取数方式，不引入新的通用多源框架。

## Problem

当前 `market-daily` 中风格轮动区块通过 `style_rotation.fetch_index_history()` 直接走 `fetch.fetch_index_data()` 的实时多源链路：

- TickFlow
- `ak.stock_zh_index_daily_em`
- `ak.index_zh_a_hist`
- `ak.stock_zh_index_hist_csindex`

这条链路对 `399376/399373` 不稳定，且仓库中没有这两个代码的 `data/archive/index_eod/*.json` 归档文件。结果是：

- GitHub Actions fresh checkout 时没有本地历史缓存；
- 风格轮动区块只能实时抓取；
- 一旦外部接口抖动，就会出现大量 warning，并退化成“无数据”。

对比之下，`style-rotation` 独立项目里这两个指数通过腾讯源同步到本地数据库后再消费，因此稳定性更高。

## Recommended Approach

采用“腾讯专用归档”方案：

1. 为 `399376/399373` 单独增加腾讯源历史抓取；
2. 在 `refresh_archive` 中把这两个指数写入 `data/archive/index_eod/399376.json` 与 `399373.json`；
3. 在风格轮动取数时优先消费这两份归档；
4. 若归档缺失或过旧，再回到腾讯实时抓取；
5. 其它指数继续保留现有实时多源逻辑。

这是最小改动且最贴近现有使用习惯的方案。

## Design

### 1. 新增腾讯源指数历史抓取能力

在 `src/valuation/fetch.py` 中新增专门面向这两个风格指数的腾讯历史抓取函数。

职责：

- 输入：裸代码（`399376` / `399373`）、起止日期；
- 调用腾讯指数历史接口；
- 统一输出为当前项目既有的标准 DataFrame：
  - `date`
  - `close`

约束：

- 只服务于风格指数历史；
- 不替换现有 `fetch_index_data()` 对其它指数的逻辑；
- 数据列要转换成与现有归档和图表代码兼容的格式。

### 2. 归档刷新纳入特殊风格指数

在 `src/valuation/refresh_archive.py` 中增加一个“风格轮动特殊指数归档”步骤。

职责：

- 固定刷新：
  - `399376`
  - `399373`
- 数据集仍落到 `index_eod`
- 归档文件命名仍使用：
  - `data/archive/index_eod/399376.json`
  - `data/archive/index_eod/399373.json`

写盘格式保持与现有 `index_eod` 一致，即每条记录至少包含：

- `trdDt`
- `pxClose`

这样风格轮动与其它读取 `index_eod` 的逻辑可以直接复用。

失败策略：

- 单独记录为风格轮动特殊指数归档失败；
- 不影响其它估值归档任务继续执行；
- 若已有本地旧归档且仍可接受，则运行侧应尽量继续消费旧归档而不是让邮件彻底无数据。

### 3. 风格轮动读取优先走归档

在 `src/valuation/style_rotation.py` / `src/valuation/fetch.py` 中为 `399376/399373` 增加特殊读取分支。

行为：

- 若请求代码是 `399376` 或 `399373`：
  - 先尝试读取 `data/archive/index_eod/<code>.json`
  - 若归档足够覆盖风格轮动所需窗口，则直接返回；
  - 若归档缺失或不够新，再调用腾讯实时抓取；
- 若请求代码不是这两个特殊值：
  - 仍使用现有 `fetch_index_data()` 多源链路。

这样市场估值邮件中的风格轮动区块，以及红利观察中用到的风格轮动 payload，会自然复用同一条稳定链路。

### 4. 红利观察与市场估值共用同一条风格数据链

不单独为红利观察复制一套逻辑。

统一目标：

- 市场估值邮件风格轮动区块；
- 红利观察中的风格挤压百分位；

都建立在同一套“腾讯源 + 本地归档”的 `399376/399373` 数据基础上。

这样有两个好处：

- 只维护一套特殊指数数据规范；
- 两个邮件看到的是同一批基础历史数据。

### 5. 日志与降噪

当前问题的一部分是 warning 噪音太大。

本次实现后应调整日志行为：

- 归档命中时，输出简短 info，例如“风格指数数据来源：archive”
- 腾讯实时补抓成功时，输出简短 info，例如“风格指数数据来源：tencent live”
- 仅在“归档不可用 + 腾讯实时也失败”时，输出完整 warning

目标不是隐藏失败，而是避免每次 CI 都刷出一长串对普通使用没有帮助的临时源报错。

## Files Expected To Change

- `src/valuation/fetch.py`
  - 新增腾讯风格指数抓取与归档优先读取逻辑
- `src/valuation/refresh_archive.py`
  - 新增 `399376/399373` 的腾讯归档刷新
- `src/valuation/style_rotation.py`
  - 风格轮动改走特殊指数归档优先路径
- `tests/test_valuation_fetch.py`
  - 新增腾讯特殊指数抓取 / 归档优先读取测试
- `tests/test_valuation_refresh_archive.py`
  - 新增风格指数腾讯归档刷新测试
- `tests/test_valuation_style_rotation.py`
  - 新增风格轮动读取特殊归档路径测试

## Out of Scope

以下内容不在本次范围内：

- 给所有指数统一接入腾讯源
- 重构整套 `fetch_index_data()` 多源架构
- 为风格轮动引入数据库
- 改动红利观察或市场估值的页面样式

## Risks

### 1. 腾讯源字段格式与现有归档不同

需要在抓取层就把数据转成项目既有归档格式，避免上层判断逻辑被迫分叉。

### 2. 周六发送依赖前一交易日数据

红利观察周六也会发送，因此风格指数归档不能只依赖“运行时现抓成功”。工作日归档必须稳定写入，周六读取前一交易日归档即可。

### 3. 归档新鲜度判断过严

若对这两个指数的归档新鲜度判断过严，周末或非交易日可能误判为过期。实现时要沿用交易数据的合理 freshness 判断，而不是机械按自然日卡死。

## Testing Strategy

必须覆盖三类测试：

1. 抓取层测试
   - 腾讯源返回成功时，能转换成标准 `date/close` 结构
   - 腾讯源返回空数据或异常时，错误可被上层识别

2. 归档层测试
   - `refresh_archive` 能为 `399376/399373` 写出标准 `index_eod` 归档
   - 内容不变时不重复写盘

3. 消费层测试
   - 风格轮动读取特殊指数时优先命中归档
   - 归档缺失时才回退腾讯实时
   - 市场估值 / 红利观察最终不会因为这两个指数的临时实时接口抖动而直接无数据

## Success Criteria

满足以下条件即视为完成：

1. `399376/399373` 在仓库中具备稳定的 `index_eod` 归档；
2. 风格轮动区块默认优先读归档；
3. 红利观察中的风格挤压百分位复用同一套特殊指数数据链；
4. GitHub Actions 中与这两个指数有关的 warning 明显减少；
5. 相关单测补齐并通过。
